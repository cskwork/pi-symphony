# Symphony for Pi v0.1 — Adversarial PRD-Compliance Review

- **PRD:** `pi-symphony-prd-roadmap/01-v0.1-pi-native-foundation.md`
- **Implementation reviewed:** commit `a844eac` ("v0.1: Symphony for Pi — Pi-native workflow foundation"), `src/` + `test/`
- **Method:** full source read of all 21 `src/**.ts` modules and all 13 test files; every claim below verified against code and, where behavior was in doubt, executed against the real modules via `vite-node` scratch scripts. Evidence is `file:line` against the reviewed commit.
- **Out of scope:** untracked working-tree files `src/web/protocol.ts` and `test/web-protocol.test.ts` (v0.2 pre-work, 16 tests) — not part of the v0.1 commit.
- **Suite status at review time:** `npm test` → 13 files / 129 tests passed; `npx tsc --noEmit` → clean. `npm run smoke:load` → **fails** (`scripts/smoke-load.mjs` does not exist).

**Verdict summary:** of the 15 functional requirements — 6 SATISFIED, 9 PARTIAL (two of them, V01-WF-001 and V01-WF-002, with *confirmed* engine-level invariant bypasses); of the 10 failure/recovery behaviors — 3 SATISFIED, 5 PARTIAL, 2 MISSING; of the 11 release gates — 2 MET, 3 PARTIAL, 6 NOT MET. The core loop is genuinely implemented and the evidence-gate engine is real, but there are two confirmed engine-level invariant violations (§6.1, §6.2), and the reviewer-isolation and TUI release gates are not verified at the depth the PRD demands.

## 1. Functional requirements

### V01-PROJ-001 — init detects metadata, no project scripts, shows proposed checks before writing — **PARTIAL**

**Implemented and safe:**
- `proposeInit` (src/init.ts:19-73) is pure read-only file inspection (`package.json`, lockfiles, `pyproject.toml`, `pom.xml`) plus read-only git via `gitSnapshot`. No script execution anywhere on the path.
- The extension shows the proposal and prompts before writing: `cmdInit` renders the proposal (src/extension/index.ts:207-223), then `ctx.ui.confirm("Initialize Symphony?")` (index.ts:224) before `c.initialize(...)`.
- `test/init.test.ts` covers Node, Python, non-Git, and malformed metadata; `core.test.ts` "initializes with only Symphony-owned paths…" asserts no product files change.

**Gaps:**
1. **Java fixture never tested.** PRD release test says "Node, Python, Java, non-Git, malformed". `pom.xml` → `mvn -q test` is implemented (init.ts:63-67) but has zero test coverage (the Python test only writes `pyproject.toml`; no pom fixture exists).
2. **Two divergent detectors.** `SymphonyCore.detectProject` (src/core.ts:113-170) duplicates the logic of `proposeInit` with *different* suggestions (`[pm, "test", "--", "--run"]` at core.ts:140 vs `[runner, "test"]` at init.ts:49). `initialize()` calls `detectProject()` for the project name while `cmdInit` displays `proposeInit()`'s proposal — the displayed checks happen to win because they are passed back in `answers.checks`, but the two code paths will drift. The unused `detectProject` is a latent contradiction source.
3. **Proposed checks are shown, not editable.** The PRD's "check suggestions" review screen implies the developer can adjust them before writing; the extension only offers prefix/branch inputs (index.ts:225-226). Minor.

### V01-PROJ-002 — only Symphony-owned paths; backup before approved overwrite — **PARTIAL**

**Implemented:**
- `initialize()` creates only `.symphony/{tasks,prompts,runtime,cache,logs}`, `config.yaml`, and `.symphony/.gitignore` (`runtime/`, `config.local.yaml`) — core.ts:203-214. Snapshot test (`core.test.ts`) confirms only `.symphony` is added and README unchanged.
- `backupFile` (src/tasks.ts:280-287) copies the old config to `config.yaml.<ulid>.bak` before overwrite (core.ts:181).

**Gaps:**
1. **"Approved overwrite" is not modeled.** The `confirmOverwrite` parameter is accepted (core.ts:178) and then read by a dead no-op branch (`if (!this.initialized || answers.confirmOverwrite !== false) { /* continue */ }`, core.ts:180-182). The core *always* backs up and overwrites; the extension uses a single generic "Initialize Symphony?" confirm for both fresh init and overwrite, with no distinct overwrite warning naming the existing config. The release-test wording "back up … before an **approved** overwrite" is only satisfied because the caller happens to confirm first.
2. **Re-init silently loses config fields.** `serializeConfigYaml` (core.ts:1016-1064) emits only `argv`/`timeout_ms`/`required` per command — `cwd`, `env_allowlist`, `max_output_bytes` (all valid schema v1 fields, config.ts:315-335) and `_unknown` preserved fields are dropped when an approved overwrite rewrites the file.

### V01-TASK-001 — collision-safe IDs, one Markdown file per task — **PARTIAL**

- `TaskIdAllocator` (src/tasks.ts:243-275) uses a persisted `.id-counter` (tmp+rename), an existence check that skips colliding files, and pads to `DEV-0NN`; `taskFileName` gives one file per task (src/paths.ts:42-44). Test covers monotonic allocation and skipping a pre-existing `DEV-003.md`.
- **Concurrency is not actually collision-safe.** The PRD release test is "concurrent creation test produces unique files"; there is no such test, and the implementation has a TOCTOU race: two processes can both read counter 0, both pick `DEV-001`, and the second `writeTaskFileAtomic` (which opens with plain `writeFileSync` on a tmp name, tasks.ts:187-190) clobbers the first. There is no exclusive-create (`wx` flag) and no lockfile. `monotonicId()` (src/ids.ts) is only monotonic *within one process*.

### V01-TASK-002 — external human edits survive machine updates — **SATISFIED**

- `parseTaskFile` segments body into human/managed spans (src/tasks.ts:38-80); `serializeTaskFile` (tasks.ts:96-99) rewrites frontmatter and managed blocks and emits human segments verbatim; `writeTaskFileAtomic` enforces expected-revision CAS and tmp+rename (tasks.ts:162-192).
- Golden-style test (`tasks.test.ts` "external human edits outside managed markers survive machine writes") passes; round-trip identity test also present.
- Caveats (not violations): keys a human adds to frontmatter are dropped (managed region, acceptable); a human line that *looks like* a managed marker would be absorbed; the PRD scenario is covered.

### V01-WF-001 — every transition validated against graph + output contract — **PARTIAL (confirmed bypass)**

**What works:**
- `assertTransition` + `TRANSITIONS` (src/workflow.ts:13-24, 47-53); `evaluateGate` applies `TRANSITION_CONTRACTS` (workflow.ts:31-38, 74-106) requiring reports/approval/fresh checks; `transition()` (core.ts:445-494) runs both before writing. Property-style test lists 10 valid and 10 invalid edges (workflow.test.ts).

**Confirmed bypass — `blocked → *` edges carry no contract:**
- `TRANSITIONS.blocked = ["plan","build","review","verify","ready","cancelled"]` (workflow.ts:19). `TRANSITION_CONTRACTS` defines **no** `blocked→X` entry, and `evaluateGate` returns `{ok:true}` whenever the contract is missing (workflow.ts:79-80).
- Executed against the real code: a task in `blocked` transitions to **`ready` with zero reports and zero checks** (`{"ok":true,"value":{"stage":"ready"}}` — scratch run §6.1). This violates G03 ("Evidence owns status"), the release gate "No required-check failure, timeout, **missing artifact**, or stale evidence can reach Ready", and the requirement's own text.
- The shipped TUI never triggers it (no "block" action is even exposed), but `transition()` is a public command on the seam v0.2 is specified to consume — this is an engine invariant hole, not just dead risk. `blocked→review`, `blocked→verify`, `blocked→build` are likewise contract-free.
- The test suite's invalid-transition list omits every `blocked→X` case, so this is untested in the wrong direction.

**Secondary gaps:**
- `recordIntegration` (core.ts:697-751) writes `stage = "postverify"` directly (core.ts:735) without `assertTransition`/`evaluateGate`, and **emits no `task.stage_changed` event** for ready→postverify (only `integration.recorded`, core.ts:748). `completeTask` similarly writes `stage = "done"` directly (core.ts:775-800), though it does evaluate the gate first. The PRD says *every* transition is validated and every mutation emits typed events; two of eight happy-path edges bypass the shared path.

### V01-WF-002 — model submits reports, cannot force transitions — **PARTIAL (engine hole at the seam)**

**What works:**
- The five registered tools (src/extension/tools.ts) expose only reads and report submissions — no `transition`, `setRunState`, `runCheckSet`, or `startAttempt` (verified by symbol search of tools.ts). Reports route through `core.submitReport` (core.ts:358-414), which auto-advances only when `evaluateGate` passes (core.ts:396-412).

**Confirmed hole — the review contract cannot distinguish independent review from self-review:**
- `sym_review_submit` (tools.ts:143-172) is registered in the *implementer's* session. Its report is written to the `review` managed section like any other.
- The `review→verify` contract is only `{ requiresReports: ["plan","implementation","review"] }` (workflow.ts:36) — it checks **presence** of a review section, never its provenance (fresh-session id, approval record, verdict).
- Executed end-to-end against the real core: after the implementer self-submits `section:"review", summary:"APPROVED — all good"`, `core.transition(task, "verify")` succeeds (scratch run §6.2). The only thing preventing this in v0.1 is that `cmdContinue`'s review case happens to always spawn the SDK reviewer (index.ts:385-412, reached from the review case at index.ts:383-384) — a UI-flow convention, not a contract. The PRD's G04/`V01-AGENT-001` invariant ("review independence") is not enforced by the engine, and the command service that v0.2 will call directly does not preserve it.
- Also: `submitReport` accepts any section in any stage (no stage/section match check, core.ts:358-393), so an implementation report can be pre-seeded during plan, etc. Harmless today, sloppy at the seam.

### V01-AGENT-001 — fresh Pi session, read-only tools, bounded manifest — **PARTIAL (implementation exists; unverified; config ignored)**

**Implemented:**
- `buildReviewManifest` (core.ts:842-889) builds a bounded manifest: contract + acceptance + risks + plan + implementation report + diff summary (≤50 paths) + `boundedDiff` (50 KB cap with deterministic "scope not fully proven" note, gitinfo.ts:112-129) + existing check evidence. **No implementer transcript enters it** (by construction — it is derived from task file + git, not session history).
- `SdkReviewerRunner` (src/reviewer.ts:87-152) creates a fresh session via `createAgentSession` with `DefaultResourceLoader({noExtensions:true, noSkills:true, noContextFiles:true, systemPromptOverride})` (reviewer.ts:106-121) — the right isolation flags — `tools: ["read","grep","find","ls"]` + a custom `sym_task_read` (reviewer.ts:126-137), and `SessionManager.inMemory()`. Malformed/missing reviewer output defaults to `changes_requested` (reviewer.ts:38-49) — never a synthesized pass.

**Gaps:**
1. **The release gate "Fresh reviewer context isolation is verified against the actual Pi SDK integration" is not met.** `reviewer.test.ts` covers only `parseReviewOutput` and prompt text. No test instantiates `SdkReviewerRunner` or inspects a child session's initial context or active tool list (the PRD's own release test for this ID). The runner has never been executed by CI.
2. **`roles.reviewer` config is validated and then ignored.** `model`, `thinking`, `max_turns: 6`, and `tools` (config.ts:100-117) are never passed to `createAgentSession` (no `model`/`thinkingLevel` args, reviewer.ts:138-145); the tool list is hardcoded (reviewer.ts:129) and differs from the documented default (`sym_task_read, sym_diff_read, read`). The Pi SDK supports `model`/`thinkingLevel` (checked against `pi-coding-agent@0.84.2` `core/sdk.d.ts`).
3. **No turn bound.** `max_turns` is unenforced and the SDK has no such option; `runFreshReview` passes no `AbortSignal` (index.ts:391-392), so a runaway reviewer session is unbounded.
4. **Reviewer session cwd is `process.cwd()`** (reviewer.ts:110), not the task repository — the reviewer's `read` tool resolves relative paths against whatever directory Pi was started in.
5. The reviewer's `sym_task_read` returns the *manifest*, not the task file its description promises (reviewer.ts:115-124) — bounded, but the tool contract lies.

### V01-QA-001 — executable + argv, mandatory timeout, output cap — **SATISFIED**

- `validateCommandDefinition` (config.ts:281-335) rejects shell strings (both `argv: "npm test | tee log"` and `unit: "npm test"` — tested), missing/invalid `timeout_ms`, and oversized `timeout_ms`/`max_output_bytes`.
- `nodeExecutor` spawns with `shell: false` (checks.ts:24) and a hard SIGKILL timer (checks.ts:25-27); output is redacted then capped (`maxOutputBytes` default 64 KB, checks.ts:63-71); environment is allowlisted to `PATH`/`HOME` + explicit entries (checks.ts:111-122, tested).
- Notes (not violations): output is buffered unbounded in memory before truncation (checks.ts:28-32) — a multi-GB-output check can OOM before the cap applies; `max_output_bytes` is optional-with-default rather than mandatory, which still yields a deterministic bound.

### V01-QA-002 — failed/timed-out required check blocks Ready and Done, no model override — **SATISFIED on the verify path (with one engine exception)**

- `evaluateGate` blocks `verify→ready` on missing/failed/timeout/unavailable/stale evidence (workflow.ts:94-103), comparing run revision to current revision (freshness). `advanceToReady` (core.ts:675-694) reruns the verify set, re-reads the revision, and gates; `transition(verify→ready)` gates too. `completeTask` gates `postverify→done` on a fresh post-integration run (core.ts:772-780).
- Tested at both engine level (workflow.test.ts, all five states) and core level (core.test.ts failed + timeout cases, incl. "even a review report cannot force the transition").
- The model has no tool that runs or writes checks; evidence cannot be forged through tool surface.
- **Exception:** the `blocked→ready` edge (§ V01-WF-001) reaches Ready with *no* checks at all — "missing evidence reaches Ready" is exactly what this requirement and G03 forbid. Done remains protected (completeTask always reruns and gates post-integration checks).
- Note: the per-command `required` flag is dead — the gate iterates `checks.verify` and requires **all** of them to pass regardless of `required: false` (workflow.ts:94-95). Stricter than spec, but it means a configured optional check hard-blocks Ready; spec'd semantics (`required`) are silently different.

### V01-GIT-001 — git ops read-only, never force/reset/clean/push/merge — **SATISFIED**

- `assertReadOnlyGit` (gitinfo.ts:28-53): subcommand allowlist (`status diff rev-parse log branch show merge-base ls-files config`) plus a `FORBIDDEN_VERBS` scan of arguments and option-embedded verbs (`--exec=push`). Every production git call goes through `gitExecFactory` which asserts first (index.ts:59-70); the check runner never touches git except read-only snapshots.
- Tests: 7 allowed + 9 forbidden argv cases, plus a command-spy test asserting a full snapshot session issues only allowlisted commands.
- Caveat: the allowlist accepts `git config <key> <value>` (mutating local config) — `config` is in `ALLOWED_SUBCOMMANDS` (gitinfo.ts:22). Read-only intent is violated in principle; nothing in Symphony calls it with a value.

### V01-REC-001 — exit during a stage recovers as Interrupted, no duplicate attempt — **PARTIAL**

**Implemented:**
- Attempts are persisted as events (`attempt.started/completed/interrupted`), replayed on construction (`restoreFromEvents`, core.ts:896-943), and `recover()` (core.ts:562-586) marks running attempts Interrupted, reclaims a stale lease, and sets task run-state to `interrupted`. `session_start` runs recovery and notifies (index.ts:84-98). `/sym continue` on an interrupted task offers exactly **Resume / Retry / Inspect / Cancel** (index.ts:285-294), and nothing resumes automatically.
- Tested: `core.test.ts` "V01-REC-001…" (dead-pid lease, attempt `plan-1` → interrupted, retry becomes `plan-2`); reviewer-crash path marks attempt interrupted with no synthesized pass (core.test.ts).

**Gaps:**
1. **Kill/restart is tested for `plan` only.** The release gate demands "abrupt termination at every active stage" (Build, Review, Verify). No test kills during build/review/verify.
2. **Resume is billed as Retry.** Both "Resume stage" and "Retry stage" start a *new* attempt (attempt counter increments, core.ts:501-531), and the counter feeds `max_stage_retries` — so with `max_stage_retries: 1`, Resume twice is refused ("stage exceeded max retries"). The PRD distinguishes Resume (continue attempt) from Retry (new attempt); the implementation only has retries.
3. **`recover()` interrupts attempts unconditionally.** Attempt records carry no owner pid/session, so a second Pi session opening in the same checkout interrupts the first session's live work; ownership is validated only for the lease file, not for attempts (core.ts:562-571). The failure table's "Validate owner PID/session before reclaim" is half-implemented.
4. Dead branch: the plan-stage retry-limit notification can never fire (`if (c.startAttempt(...) && !c.getTask(...).ok)` — index.ts:311-313 is logically unreachable).

### V01-UI-001 — core operations usable at 80×24, no horizontal scroll — **PARTIAL**

- Widget is hard-capped at 2 lines (core.ts:811-834; tested). The overlay truncates every line to the render width (`fit`/`truncateToWidth`, overlay.ts:160-200), and `overlay.test.ts` asserts ≤80 cols / ≤22 rows at width 80, wide side-by-side at 160, keyboard navigation (j/k/enter/tab/esc), Escape closing without mutation, and text (not color) carrying stage meaning.
- **Gaps:**
  1. **No height bound.** `render(width)` (overlay.ts:127) never receives or respects terminal height: a task list with >18 tasks or a detail pane (presentation.ts caps review at 24 lines, others uncapped) overflows 24 rows — the exact "usable at 80×24" claim. There is no scrolling/pagination.
  2. **PRD snapshot matrix not met.** No snapshots at 110×30; no keyboard-only smoke test of the real overlay wiring (`ctx.ui.custom` path is never exercised in tests — `openOverlay` runs only under `mode === "tui"`, and all wiring tests use `mode: "print"`).
  3. **Overlay actions target the wrong task.** `runOverlayAction` re-selects the *first active* task (index.ts:585) instead of the task highlighted in the overlay (the model was built for `selectedId`); with two active tasks, "Record integration…"/"Complete"/"Cancel" act on DEV-001 even when DEV-002 is selected. Likewise `cmdComplete`/`cmdChecks`/`cmdPause` always pick the first active task.

### V01-SAFE-001 — protected-path writes & destructive commands blocked/confirmed — **PARTIAL**

- Guard: `tool_call` interception (index.ts:110-153) classifies write/edit paths via glob `minimatch` (guard.ts:19-34, extension/minimatch.ts) against `security.protected_paths`, honoring `protected_path_policy: block|confirm`; bash commands are screened by 9 destructive patterns (guard.ts:16-26). Confirmations name the path/command and cwd, and repeat the not-a-sandbox warning.
- Tests: interception matrix in guard.test.ts (protected/normal paths, confirm vs block, destructive vs benign) plus wiring-test coverage of block/decline/allow through the real handler.

**Gaps (adversarial):**
  1. **Bypassable regexes:** `rm -fr /` does not match `rm\s+(-[a-zA-Z]*r[a-zA-Z]*f|…)` (the pattern requires `r` before `f` within one token); `git -C <dir> push` evades `\bgit\s+push\b`; `git restore`, `chmod -R`, `dd`, `truncate`, output redirection (`echo x > .env`) are all unlisted.
  2. **Protected paths are bypassable via the bash tool:** `echo "X=1" > .env` or `rm .env` never reach the path classifier (it only inspects write/edit tool inputs). The PRD's "protected-path writes … must be blocked or explicitly confirmed" holds only for the write/edit tools.
  3. **Tool-name coverage assumption:** only `write`, `edit`, `bash` are intercepted; any other Pi write-capable tool name (e.g. `apply_patch`/`str_replace`/`multi_edit`, if present in a Pi version) bypasses entirely.
  4. The confirm-*allow* branch (user approves a protected write) is untested — the wiring test only exercises decline.

### V01-COMP-001 — `/sym complete` verifies integrated revision, reruns post-integration checks against it — **SATISFIED**

- `recordIntegration` (core.ts:697-751) requires stage `ready`, verifies the revision is contained in the local target branch (`git branch --contains <rev> --list <branch>`, gitinfo.ts:152-160), rejects with a specific cause (nonexistent commit vs not-on-branch — tested), and records actor/revision/branch/time into frontmatter + `integration` managed section + event.
- `completeTask` (core.ts:753-812) re-verifies the revision is still on the target, **requires the current checkout to be exactly the integrated revision** (core.ts:766-771 — the E2E proof the PRD's "changes target checkout and confirms evidence revision" asks for), reruns the post-integration set, gates on fresh passing evidence, and writes a closeout section with per-check statuses. Full lifecycle E2E + rejection tests pass.
- Caveats: target is matched against the *local* branch only (a `origin/main`-style target never matches); in a **non-Git** repository integration can never be recorded (`branch --contains` fails → rejected), so Done is unreachable in non-Git repos — see failure table "Git unavailable".

### V01-CORE-001 — all mutations via UI-independent command service emitting serializable events — **SATISFIED (with ledger completeness defect)**

- `SymphonyCore` (src/core.ts) is UI-independent (deps-injected `UiPort` is never invoked by core); the extension layer calls commands only — verified by reading all of `extension/index.ts`, `tools.ts`, `overlay.ts`: the TUI never opens a task file for writing. `overlay.ts` is a pure component; `openOverlay` projects via `buildModel` and dispatches actions back to commands.
- Events are serializable JSONL with the PRD envelope fields (`EventLedger`, events.ts:14-58), torn-tail tolerant (events.ts:88-107, tested), per-aggregate sequenced, and replayed into the in-memory projection (`replay`/`restoreFromEvents`, core.ts:882-941). `replayEvents` exists for external consumers (tested).
- Wiring test drives the real extension factory through the command surface only.
- **Defects:** (a) ready→postverify emits no `task.stage_changed` (see V01-WF-001) — an event-sourced v0.2 client will compute a stale stage; (b) sequence numbers are per-task-stream, while the PRD says "local to the repository event stream"; (c) `lease.reclaimed` is declared in `EVENT_TYPES` but never emitted; (d) `recovery.completed` is appended under aggregateId `"runtime"`.

## 5. Contradictions and forgeable-evidence findings (adversarial)

Confirmed by execution (marked ✦); rest by code reading.

1. **✦ `blocked → ready` with zero evidence** (workflow.ts:19 + :79-80; §6.1). Direct contradiction of G03 and the Ready gate.
2. **✦ Self-submitted review satisfies `review→verify`** (tools.ts:143-172 + workflow.ts:36; §6.2). The implementer model can write an "APPROVED" review section; the engine contract cannot tell it from an independent review. Only the TUI flow protects this today.
3. **✦ Plan-approval policy ignores risks discovered during planning.** `sym_plan_submit` accepts `risks` ("Newly identified risks", tools.ts:81) but they land in report details only; `needsPlanApproval` reads frontmatter `risks` captured at task creation (workflow.ts:109-114; core.ts:396-401). A task created without risks that planning reveals to be risky auto-advances to build with no approval — the `risks_only` policy is evadable by omission.
4. **✦ Widget AC progress is always `N/N`.** `const acDone = active.acceptance.length` (core.ts:818) — the PRD's sample "AC 2/3" is impossible; the widget displays unearned progress as earned. (Overlay shows only `acceptanceTotal` too; `acceptanceStatus` from build reports is never aggregated.)
5. **✦ Lease mutual exclusion is decorative.** `LeaseManager.acquire` overwrites unconditionally (lease.ts:29-35) and `startAttempt` never checks `lease.status()` first (core.ts:501-531) — a second live lease replaces the first silently. "One execution lease per checkout" (capability 6) is not enforced; combined with un-enforced `workspace.max_active_tasks` (validated to be 1 at config level, config.ts:141-144, but `createTask` never checks how many active tasks exist) multiple tasks can run concurrently.
6. **Ready→postverify stage change bypasses the transition engine and the ledger** (core.ts:735, :748; §V01-WF-001). Event-sourced consumers (v0.2) will compute a wrong stage.
7. **Guard regexes and tool-name coverage are bypassable** (§V01-SAFE-001): `rm -fr`, `git -C . push`, `git restore`, bash output redirection to protected paths, non-write/edit tool names.
8. **Config surface validated but never applied:** `roles.*` (planner/implementer briefs are hardcoded strings; reviewer config ignored — §V01-AGENT-001), `workflow.review_medium_policy` (review always runs the fresh SDK reviewer regardless of `ask`/`current` (review case index.ts:352-354 → runFreshReview index.ts:385-412)), `workflow.completion`, `workflow.preset`, `ui.density`, `config.local.yaml` (parsed into `LoadedConfig.local`, config.ts:358-366, then never read by anything — presentation overrides do nothing), per-command `required` flag (gate ignores it, workflow.ts:94-95).
9. **Re-init destroys valid config fields** (`env_allowlist`, `max_output_bytes`, `cwd`, unknown preserved fields) via `serializeConfigYaml` (core.ts:1016ff; §V01-PROJ-002).
10. **Overlay/action targeting bug** — actions apply to the first active task, not the selected one (index.ts:585; §V01-UI-001).
11. **Not found (explicitly checked):** the TUI never mutates task Markdown directly — every mutation goes through `SymphonyCore` commands; the overlay is a pure projection. No `shell:true` anywhere. No telemetry leaves the machine. These PRD invariants hold.

## 8. Top 10 gaps by severity

1. **[BLOCKER] `blocked → ready` transition carries no output contract — Ready reachable with zero evidence.** workflow.ts:19, :79-80. Violates G03 and the release gate "no missing evidence reaches Ready". Fix: define `blocked→X` contracts (or require re-entering the prior stage) and property-test all graph edges in both directions.
2. **[BLOCKER] Review independence is not an engine invariant — self-submitted review satisfies `review→verify`.** tools.ts:143-172, workflow.ts:36. The implementer model can self-certify via `sym_review_submit`; only the TUI flow prevents it, and the v0.2 command seam will call `transition` directly. Fix: gate on provenance (fresh-session approval record / reviewer session id), not report presence; restrict `sym_review_submit` to reviewer sessions.
3. **[MAJOR] Reviewer isolation unverified against the real Pi SDK, and reviewer role config ignored.** No test instantiates `SdkReviewerRunner` (release gate explicitly requires it); `roles.reviewer` model/thinking/max_turns/tools never applied (reviewer.ts:87-152); no turn/abort bound; reviewer cwd = `process.cwd()`.
4. **[MAJOR] "Evidence artifact missing → Broken + invalidate pass" is unimplemented.** types.ts:41 has no `broken` status; deleting check artifacts leaves gates green (core.ts:943-985 only rehydrates). Release gate "missing artifact cannot reach Ready/Done" is therefore unenforceable as written.
5. **[MAJOR] Plan-approval policy evadable — risks discovered during planning never trigger approval.** tools.ts:81 vs workflow.ts:109-114 (✦ demonstrated). `risks_only` protects only creation-time risks.
6. **[MAJOR] Recovery/lease semantics weaker than specified.** Kill/restart tested for plan only; `recover()` interrupts attempts without owner validation and reclaims stale leases with no confirmation; lease acquisition overwrites live leases (✦); Resume and Retry are the same operation and both consume the retry budget; unreadable leases are never reclaimed.
7. **[MAJOR] TUI release gate not met.** No height bound → overflow at 80×24 with realistic task counts; no 110×30/160×45 snapshots; no keyboard-only smoke through the real overlay; overlay/command actions target the first active task instead of the selected one (index.ts:585).
8. **[MAJOR] Packaging/release engineering absent.** `npm run smoke:load` fails (missing `scripts/smoke-load.mjs`); no install/trust/reload/upgrade/uninstall smoke; no `files` allowlist; `docs/` is empty while README points to it; no cross-platform (Windows CRLF/path) handling — four release gates unmet.
9. **[MINOR] Config surface validated but inert, and re-init loses fields.** `review_medium_policy`, `completion`, `preset`, `ui.density`, `config.local.yaml`, per-command `required` all unused; `serializeConfigYaml` drops `env_allowlist`/`max_output_bytes`/`cwd`/unknown fields on approved overwrite; `max_active_tasks: 1` and `max_child_sessions` unenforced.
10. **[MINOR] Misleading/incorrect status surfaces.** Widget AC progress always shows `N/N` (✦ core.ts:818); `stale` check status is never displayed as a state (staleness only appears in gate refusal text); `sym_task_read` in the reviewer returns the manifest, not the task file; non-Git repositories can reach Ready but never Done, contradicting "continue non-Git workflow".
