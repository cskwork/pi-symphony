# Symphony for Pi — PRD-compliance review: v0.2 → v1.0

**Reviewed:** `pi-symphony` @ `6a45ff6` (v1.0.0), working tree clean.
**Scope:** every functional requirement `V02-*` … `V10-*` in the PRD roadmap (162 requirements), plus regression analysis against v0.1 invariants and judgment of documented scope deferrals.
**Method:** read every PRD in full; read every source file under `src/` and every test under `test/` at HEAD; verified cross-wiring by import-grepping which v0.3+ modules are actually reachable from the extension/runtime; ran the full suite (299/299 pass) and wrote a throwaway test to check the v1→v2 migration round-trip against the real config loader.

(162 requirements total: V02×15, V03×15, V04×15, V05×18, V06×19, V07×17, V08×18, V09×21, V10×24.)

The single dominant pattern: **v0.5–v0.9 are "library shelves," not product features.** `worktrees.ts`, `scheduler.ts`, `runtime-supervisor.ts`, `integrations.ts`, and `hardening.ts` are never imported by `src/extension/index.ts`, `src/core.ts`, or `src/web/*` (verified by import grep — their only non-self importers are their own test files). The v0.1 task engine, the v0.2 web layer, and the v0.3/v0.4 skills+delegation tools are genuinely wired; nearly everything after v0.4 ships as pure functions with unit tests. The version reports and CHANGELOG describe these libraries in product language ("Supervisor authority…", "deterministic scheduler", "push preflight"), which materially overstates what a user can do.

Second finding (blocker, experimentally verified): **the v0.3 schema migration writes a config the product cannot load.** `previewMigration` emits `version: 2` (`src/migration.ts:28`), but the only config loader rejects any version ≠ 1 (`src/config.ts:124` "unsupported schema version … (v0.1 supports version 1 only)"). Applying the migration puts the repository into permanent `configuration is invalid` read-only mode until the backup is manually restored. `migration.test.ts` imports `loadConfigFromText` but never asserts against it, hiding the defect.

  message: "unsupported schema version 2; run /sym init to migrate (v0.1 supports version 1 only)" }]

## Cross-cutting findings

### A. The "library shelf" pattern (v0.5–v0.9 unwired)

Import graph at HEAD (only non-test consumers shown):

| Module | Shipped in | Imported by product code? | Product impact |
|---|---|---|---|
| `worktrees.ts` (typed git, registry, fenced leases, preflight) | v0.5 | **No** | No workspace is ever allocated; `renderGitCommand` is never executed; the task lifecycle remains `current_checkout` with manual `recordIntegration` |
| `scheduler.ts` (DAG, selection, dispatch, capacity, retry) | v0.6 | **No** | No queue anywhere; `config.ts:162` still enforces "v0.1 allows exactly 1 active task"; no SQLite exists in the repo (grep: zero hits) |
| `runtime-supervisor.ts` (authority, epochs, idempotent RPC, detach contracts, timers) | v0.7 | **No** | No supervisor process, no Unix-socket IPC, no headless CLI (`package.json` has no `bin`), no detach flow; `/sym web` still owned by the Pi process |

Each module has decent unit tests, so "tests pass" is true while the *product* behaviors the PRDs specify (allocate a worktree, schedule two tasks, detach and close Pi, open a PR, refuse an unsupported host at startup) do not exist.

### B. Schema v2 migration defect (blocker)

* `src/migration.ts:28` writes `version: 2`; `src/config.ts:118-127` rejects `version !== 1` and returns issues; `SymphonyCore` then runs with `configIssues.length > 0`, which blocks `createTask`, `runCheckSet`, `advanceToReady`, `completeTask` ("configuration is invalid").
* The migration is not reachable from any `/sym` command or web route (only tests call it), so users cannot currently trigger it — but the README ("Repositories can define a validated stage graph in `config.yaml` (schema v2)"), CHANGELOG 0.3.0 ("config v1→v2 migration"), and `docs/v1.0-report.md` ("Schema v1 (migrated to v2 with preview/backup/rollback)") all document it as a supported product behavior. Following the documented behavior bricks the repo config until the `.v1-backup-*` file is restored by hand.

### C. v0.2 `config/apply` is a second mutation path around SymphonyCore

`src/web/server.ts:404-430` (`configApply`): the HTTP adapter itself does `writeFileSync(tmp, draft)` + `renameSync` on `.symphony/config.yaml` (`server.ts:415-417`) and then pushes a synthetic `config.applied` event only into the in-memory SSE ring (`server.ts:418`, `EventBridge.publish`) — not into the durable `EventLedger`. This directly violates the v0.2 release gate "No frontend or HTTP adapter path writes task/config files directly" and the executive decision that the adapter "contains no business rules." Consequences: after a server restart the config-apply history is gone; the core's `this.config` is stale until `coreFactory()` is next called (the code works around this by constructing a fresh core, `server.ts:411`); and nothing equivalent to core's `config.applied` audit exists in the ledger. Task-file mutations, by contrast, do go through `SymphonyCore` (verified by `web-lifecycle.test.ts` "byte-identical to the same core mutation").

## Did later versions weaken earlier guarantees?

1. **v0.2 weakened the single-writer claim (real, wired).** `configApply` gives the HTTP adapter a direct file-write path to `.symphony/config.yaml` and a non-durable synthetic event (Finding C). v0.1's invariant was "SymphonyCore is the only component that mutates task state"; the config file is now mutated by two components (core's `initialize`/serializer and the web adapter's raw text write), and they disagree: `core.ts serializeConfigYaml` renders normalized snake_case YAML, while apply writes the user's raw draft verbatim. A browser apply after `/sym init` changes nothing functionally, but the two writers have no shared revision model at the file level (only the hash check).
2. **v0.3 did not weaken the check/review gates — because it never reaches them.** `compileWorkflow` preserves review provenance as a compile-time invariant (any review-report output forces `requiresReviewProvenance`, `workflow.ts:239-247`), and the static engine is untouched. The weakening is *coverage*, not enforcement: customization is inert, so no custom graph can bypass or alter the v0.1 gates.
3. **v0.4 weakened the (specified) handoff acceptance discipline in the only wired path.** `cmdDelegate` auto-accepts and auto-completes handoffs as actor "system" immediately after submission (`extension/index.ts:699-702`), with no idle/matching/policy preconditions — the library enforces V04-HOF-005's checks, but the product never exercises the acknowledgment boundary it was built for.
4. **v0.6/v0.7 create no second mutation path — they create none at all.** Neither the scheduler nor any RPC surface is reachable, so `SymphonyCore` remains the sole mutation authority in practice. The residual risk is *documentation*: the v1.0 report presents "idempotent RPC/dispatch/outbound operations, fenced leases, typed git mutations only" as product guarantees backed by "all module tests" — those are unit tests of unwired code.
5. **Phantom evidence references (new integrity smell).** Every real delegated handoff cites `.symphony/evidence/<task>/review/<role>-<session>.md` with a digest, and the file is never created (`extension/index.ts:696`). Under v0.1's evidence discipline (digest-bound artifacts), this is a reference to evidence that does not exist — the handoff audit trail cannot be verified after the fact.
6. **Unbounded audit memory (small but real):** `WebControlPlane.audit` grows without bound for the process lifetime (`server.ts:26`), unbounded SSE subscribers per server — contra the v0.9 resource-bounds posture.
