# Symphony for Pi v0.1 — Adversarial Review

**Scope:** committed v0.1 tree (`a844eac`), `src/` + `test/`, reviewed against README safety claims and the v0.1 PRD (G03, G05, V01-WF-002, V01-QA-002, V01-SAFE-001, failure table).
**Method:** full source read; 24 attack repros executed out-of-tree against a pinned snapshot of `a844eac` (harness: `/tmp/sym-repro`, snapshot: `/tmp/sym-v01`; re-run with `npx vitest --run --config /tmp/sym-repro/vitest.config.ts`). No repo files were modified except this report.
**Baseline:** all 13 v0.1 test files pass (129 tests). `npx vitest --run` on the *working tree* currently reports 140 tests / 3 failures — the failures are all in untracked v0.2 work-in-progress (`test/web-server.test.ts`, `src/web/`) being developed concurrently, not in v0.1. The working tree is also being actively patched mid-review (see "Concurrent fixes" below); all file:line references below are pinned to `a844eac`.

**Verdict:** the in-process, happy-path guarantees are real and well-tested: a failed/timed-out/unavailable required check cannot reach Ready or Done through `advanceToReady`/`completeTask`, task writes are atomic CAS, the reviewer session is genuinely fresh and read-only, and crash ordering fails safe. But the trust boundary is drawn in the wrong place: **everything the gates rely on (task frontmatter, config, evidence artifacts, ledger) lives in files the guarded tools can still write — and `bash` can write anything with zero interception.** Every "cannot be bypassed by the model" claim in the README is therefore falsifiable by a hostile model with write/bash access. Several of these are already being fixed in the uncommitted working tree (noted per finding).

Severity: **blocker** = breaks a headline promise with a model-reachable path; **major** = integrity/availability hole or requires an adapter/second process; **minor** = hardening, spec gap, or narrow edge.

## 1. Evidence integrity

### E1 · BLOCKER — Workflow state is client-trusted text; the guard does not protect it
`src/extension/index.ts:110-141` (tool_call guard), `src/config.ts:94` (default `protectedPaths`), `src/core.ts:302-330` (`listTasks`/`getTask` trust frontmatter), `src/core.ts:882-894` (`replay()` never reconciles file vs ledger).

The default protected paths are `.env`, `.env.*`, `.git/**`, `.symphony/runtime/**` — with policy `confirm`. **`.symphony/tasks/**`, `.symphony/evidence/**`, and `.symphony/config.yaml` are unprotected**, and the `bash` tool is only scanned for nine destructive-command regexes, so `echo`/`sed`/`tee` write any file with no interception at all.

Repro (R1): task `DEV-001` in backlog; `writeFileSync(tasks/DEV-001.md, text.replace("stage: backlog","stage: done"))` — one write-tool call the guard classifies as `allow`. `listTasks()` reports `done`, the widget shows no active task, and the ledger has no `done` event. Nothing ever compares file stage against ledger stage, so the forgery is permanent and invisible.
Repro (R2b): edit `config.yaml` to `checks: {verify: [], post_integration: []}` (still schema-valid), restart, `/sym continue` in verify → **Ready with zero checks executed** (`advanceToReady` at `core.ts:675-690` gates on an empty required list). The config edit changes `configHash`, but `pinnedConfigHash` is recorded and never checked anywhere (grep: only written, `core.ts:518`), so nothing re-approval-gates it.

Minimal fix: (1) default `protectedPaths` to `[".env*", "**/.env*", ".git/**", ".symphony/**"]` with policy `confirm` for `config.yaml` and `block` for tasks/evidence; (2) on load, reconcile `frontmatter.stage` against the last `task.stage_changed` event and refuse to act on a task whose file stage has no ledger event (quarantine to `blocked` with a doctor line); (3) enforce `pinnedConfigHash`: if `configHash` changed since the attempt pinned it, require re-confirmation before Ready/Done.

### E2 · BLOCKER — Replay trusts on-disk evidence and ledger lines with no integrity binding
`src/core.ts:951-1008` (`recordCheckEvidenceFromEvent`), `src/events.ts:20-64`.

Two independent forges, both surviving restart:
- **Artifact forge (R2):** run a failing verify (blocked, correctly). Rewrite the artifact `.symphony/evidence/DEV-001/checks/unit-*.json` to `status:"passed"` with a later `finishedAt`; restart. `recordCheckEvidenceFromEvent` rehydrates the disk artifact whenever `evidence.finishedAt >= current.finishedAt` — the forged artifact wins over the event. The in-memory projection now says `passed`.
- **Ledger forge (R3):** `sed 's/"status":"failed"/"status":"passed"/'` on `runtime/events/DEV-001.jsonl`; restart; replay reports `passed`.

On top of R1 this yields a full forged Ready: forged artifact + restart + any caller of `core.transition(id,"ready")` (the v0.2 web plane in `src/web/server.ts:278` already exposes exactly that call) reaches Ready with a genuinely failed check. Even in the v0.1 TUI, the forged projection poisons the overlay, doctor, and `nextStep` advice.

Minimal fix: the ledger event is the only machine-written record the model can't cheaply rewrite *if* the runtime dir is actually protected — bind artifacts to events by storing `sha256(artifact)` in the `check.completed` event and verifying it on rehydrate; on mismatch mark the run `broken` (status already exists in the type) instead of trusting either side.

### E3 · MAJOR — `transition()` evaluates check freshness with `currentRevision: null`
`src/core.ts:456` (gate call inside `transition`), `src/workflow.ts:100` (staleness only checked when `currentRevision !== null`).

`advanceToReady`/`completeTask` re-read HEAD and gate on fresh revision — good. But the generic `transition()` passes `revision: null`, which silently disables the staleness rule for every edge it evaluates (`verify→ready`, `postverify→done`).

Repro (R4): task in verify; `runCheckSet` passes at revision R1; commit R2; new core; `core.transition(id, "ready")` → **ok** with evidence pinned to R1. `advanceToReady` on the same state correctly refuses. Any adapter calling `transition` (web WIP does, `src/web/server.ts:278`) gets the stale-accepting path.

Minimal fix: make `requiresChecks` edges refuse to evaluate without a fresh revision (pass the real HEAD into `transition`'s gate, or route all check-gated transitions through the async paths only).

### E4 · MAJOR — The review gate cannot tell an implementer-written review from a fresh one
`src/workflow.ts:35` (`review→verify` only requires *a* review report), `src/extension/tools.ts:143-168` (`sym_review_submit` is callable by any session, verdict included).

Repro (R5): drive to `review`; call `submitReport(section:"review", details:{verdict:"approved"})` as the implementer; `transition(id,"verify")` → **ok**. In v0.1 the TUI's `/sym continue` happens to always run the SDK reviewer first (`runFreshReview`, `index.ts:392-421`), so the hole is reachable only via direct core calls today — but the gate, which is the documented invariant layer, is satisfied by self-certification. *Concurrent fix:* the uncommitted working tree adds `requiresReviewProvenance` + report `origin` — right approach; verify replay restores provenance too.

### E5 · MAJOR — Plan approval never expires; a re-plan inherits the old approval
`src/core.ts:416-443` (`resolveApproval`), `src/core.ts:396-414` (new plan report does not clear approvals), `src/workflow.ts:82-88`.

Repro (R6): task with risks; plan #1 approved → build; `build→plan` (allowed); submit a much riskier plan #2 (approval re-requested, no auto-advance); `core.transition(id,"build")` → **ok** — the gate's `planApproved` is still the entry from plan #1.
Minimal fix: store `approvedPlanRevision` in the approval record and require `approval.inputRevision >= revision-of-latest-plan-report`; a new plan report invalidates prior approvals. (The uncommitted diff merges *newly declared* plan risks into the contract, which is good, but does not invalidate the old approval.)

### E6 · MINOR — Missing evidence artifact does not invalidate a pass (PRD failure-table violation)
`src/core.ts:951-1008`. PRD: "Evidence artifact missing → mark the reference Broken and invalidate any pass that depends on it." Repro (R18): delete `evidence/DEV-001/checks/`; restart; projection still reports `passed` from the event. *Concurrent fix:* uncommitted `validateEvidenceArtifacts` downgrades passes with missing artifacts to `broken` — matches the PRD.

### E7 · MINOR — ID reuse resurrections
Task ids come from `.symphony/tasks/.id-counter` + filename existence (`src/tasks.ts:246-262`). Delete a task file and the counter (or clone a repo where runtime/events/ was copied but tasks/ pruned) and a new task reuses `DEV-001`; `restoreFromEvents` then replays the **old** task's approvals/checks onto the new task (`core.ts:896-949`). Low likelihood, high confusion. Fix: embed a random suffix in task ids or key replay on creation-event lineage, not the id string.

## 2. Crash safety (kill at any await point)

**What holds (verified by code trace + their restart test):** task-file writes are parse→CAS→unique-tmp→`renameSync` (`tasks.ts:158-197`); the ledger is append-only JSONL with torn-tail tolerance (`events.ts:67-86`); mutation ordering is **file first, event second** everywhere, so a crash between them loses *event* evidence, which fails gates closed (R20: plan written, event lost → `transition plan→build` refuses until resubmitted — availability loss only, never a false pass). Lease windows also fail safe: crash after acquire before events → stale lease (dead pid) reclaimed by `recover()`.

### C1 · MINOR — `truncateTornTail` rewrites the ledger non-atomically
`src/events.ts:83`: `writeFileSync(file, valid.join("\n"))` — a crash mid-rewrite truncates the valid prefix of the event stream (lost approvals/check evidence, gates fail closed but users must re-approve/rerun). Fix: write `file.tmp` → rename, same as everywhere else. Related: no `fsync` anywhere (`tasks.ts:190-196` claims "fsync directory entry via rename" — rename is atomic, not durable; power loss can lose both file and events). Fix: `fsync` file + parent dir on task/ledger/lease writes if power-loss durability is claimed.

### C2 · MINOR — Report evidence is duplicated, not derived
`hasReport` comes only from `report.submitted` events (`core.ts:896-949`); the rendered section in the file is never consulted. Crash between write and append (R20) or a torn-tail drop (§Concurrency) silently "forgets" a submitted plan/review that is visibly present in the file. Fix: on load, if the file's managed section hash differs from the last event's, surface a doctor warning (and optionally re-derive `hasReport`).

### C3 · MINOR — `runCheckSet` persists artifact before event
`core.ts:615-641`: crash between `persistCheckEvidence` and `check.completed` → orphan artifact; replay ignores it (safe). Crash between `runs.set` and artifact write → nothing persisted (safe). No fix needed beyond E2's hash binding, which also cleans up orphan artifacts.

## 3. Concurrency (two cores / two pi processes)

### K1 · MAJOR — The execution lease provides no mutual exclusion
`src/lease.ts:29-34` (`acquire` unconditionally overwrites; no holder check), `src/core.ts:521-534` (`startAttempt` acquires without checking). Repro (R9): manager A holds a live lease; B `acquire`s → silently stolen. Two cores on one checkout both run attempts; nothing at the task-mutation layer consults the lease. *Concurrent fix:* uncommitted `acquire` now refuses live foreign owners and `startAttempt` propagates the refusal — correct direction; keep the pid-reuse caveat below.

### K2 · MAJOR — `recover()` interrupts a *live* worker's attempts
`src/core.ts:562-589`: any new core instance (session start!) marks every running attempt `interrupted` and stomps `runState`, with no ownership check — attempt records don't even store the owning pid. Repro (R9): core A starts an attempt; core B (second pi) `recover()` → ledger gains `attempt.interrupted` for A's live attempt and the task flips to `interrupted` under A's feet. *Concurrent fix:* uncommitted `recover` skips when a foreign live owner holds the lease — but attempts still carry no pid, so the guard only works while the lease file is intact. Fix properly: persist `pid`/`sessionId` on `AttemptRecord` and validate before interrupting.

### K3 · MAJOR — Task id allocation races: duplicate ids and a hard crash
`src/tasks.ts:246-276`: `readCounter → existsSync → writeCounter` with no lock, and the counter tmp path is **fixed** (`.id-counter.tmp`, line 273).
Repro (R10, 8 concurrent processes, wall-clock barrier): observed both failure modes — (a) two processes both allocated `DEV-001` (one task file silently overwritten by the other's `writeTaskFileAtomic`), and (b) `ENOENT: rename '.id-counter.tmp'` thrown out of `next()` → `createTask` throws an unhandled exception (extension `cmdNew` has no catch) instead of returning an error result. PRD V01-TASK-001 claims "collision-safe under concurrency".
Fix: create the task file with `openSync(..., "wx")` as the claim (O_EXCL is the lock), then bump the counter; unique tmp names for the counter; wrap `createTask` in try/catch → CommandResult.

### K4 · MAJOR — Attempt ids collide across tasks (global map keyed by `stage-n`)
`src/core.ts:512` (`id: \`${stage}-${priorTries+1}\``), map at `core.ts:520`. Repro (R8): `startAttempt(DEV-001,"plan")` → `plan-1`; `startAttempt(DEV-002,"plan")` → also `plan-1`, **overwriting** DEV-001's record; `completeAttempt(DEV-001,"plan-1")` now fails `attempt.taskId !== taskId`, so DEV-001's attempt can never complete and its lease release is skipped. Note `workspace.maxActiveTasks: 1` is never enforced (`createTask`, `core.ts:264-301`), so multiple active tasks are one `/sym new` away. Fix: key attempts `${taskId}:${stage}-${n}`; enforce maxActiveTasks in `createTask`.

### K5 · MINOR — Two ledger writers interleave
Two processes appending the same aggregate use independent sequence caches (`events.ts:22-64`) → duplicate/out-of-order sequence numbers, and one process's `truncateTornTail` rewrite can drop the other's tail events. Fail-closed (E6-style evidence loss) but real. Fix: single-writer via the lease (K1) or per-stream lock file.

## 4. Data loss in task files (marker parser/writer)

### D1 · MINOR — CRLF task files become unreadable and unwritable
`src/tasks.ts:50,57`: parser requires literal `---\n` / `\n---\n`. Repro (R13): save `DEV-001.md` with CRLF (Windows/macOS editor) → every `parseTaskFile` throws, `getTask` errors, and every machine write (`setRunState` etc.) fails — the task is bricked until a human fixes line endings. Fix: normalize `\r\n` → `\n` on read; write `\n` (status quo).

### D2 · MINOR — Managed-marker ambiguity corrupts section ownership
`src/tasks.ts:57-85` (parser picks the first start and the first matching end of the same section), `tasks.ts:203-230` (`setManagedSection` replaces only the first segment).
Repro (R14a): append a second stale `<!-- symphony:plan:start -->…end` pair in the human area; submit a new plan → the machine replaces the *first* block and the **stale duplicate survives** as a second machine-looking plan section (two `symphony:plan:start` markers in the file, overlay shows both).
Repro (R14b): human notes written between marker-lookalike comments are parsed as a managed segment and **silently destroyed** by the next machine write to that section — the README promise only holds for text *outside* markers, and nothing warns the human.
Fix: on write, collapse duplicate sections for the same id to the last one and demote orphan markers in human text (escape the leading `<`); on read, flag files whose managed-marker count ≠ 1 per section in doctor.

### D3 · MINOR (notes) — Frontmatter is machine-owned and lossy on rewrite
Any human-added frontmatter key is dropped on the next machine write (`toYamlFrontmatter`, `tasks.ts:134-150`); `revision` defaults to 1 when missing (`tasks.ts:104`). Document it or preserve unknown keys like config does (`_unknown`).

## 5. Security (guard, redaction, git allowlist)

### S1 · MAJOR — Protected-path defaults miss the realistic cases
`src/config.ts:94`, `src/extension/guard.ts:28-34`, `minimatch.ts`. Repro (R11), all with default policy:
- `backend/.env`, `frontend/.env.local` → **allow** (patterns are anchored, no `**/` prefix — nested env files, the common monorepo layout, are unprotected).
- `.envrc` (direnv, usually sources secrets) → allow (`.env`/`.env.*` don't match).
- `.ENV` → allow; on default case-insensitive APFS this overwrites `.env`.
- `../victim/.env` (outside cwd) → `pathRelativeTo` returns the absolute path, which matches no repo-relative pattern → allow.
- `gitlink/config` where `gitlink → .git` (symlink) → allow: `resolveToolPath`/`pathRelativeTo` are purely lexical; **no `realpath` anywhere in the package** (grep verified).
Fix: patterns `**/.env*`, `**/.env.*`, plus realpath the target (and each existing parent) before classification, and case-fold the comparison on darwin/win32.

### S2 · MAJOR — The `bash` guard is nine regexes; everything else is invisible
`src/extension/guard.ts:16-26`, `index.ts:135-141`. Repro (R11): `echo 'LEAK' > .env`, `git -C .. push --force`, `git checkout .` (discards work), `find . -name '*.ts' -delete`, `sed -i … .symphony/tasks/DEV-001.md` — all pass with zero confirmation. Combined with E1 this is the practical bypass of every stated protection. Honest fix for v0.1: extend `findDestructiveCommand` to also flag redirect/tee targets matching protected patterns and `git -C <dir>` forms; state plainly in README that bash is not intercepted (the current README half-implies it is).

### S3 · MAJOR (latent) — Git allowlist admits `config` (write-capable) and file-writing options; `--opt=verb` trailing verbs escape the matcher
`src/gitinfo.ts:6-15, 48-56`. Verified: `assertReadOnlyGit(["config","user.email","evil@x"])` and `["diff","--output=/tmp/evil","HEAD"]` pass; `["log","--exec=push"]` also passes the matcher (the `verb=` substring check misses a trailing verb — git itself rejects `--exec` on `log`, which is the only reason this is not exploitable). No v0.1 call site passes user-controlled options except `revisionOnBranch`'s revision/branch (`gitinfo.ts:150-160`), and options like `--output` aren't valid there, so today it's hardening, not a hole — but the allowlist is the security boundary the PRD leans on. Fix: allow `config` only with `--get*`; reject any `-`-prefixed arg not on a per-subcommand option allowlist rather than a verb denylist.

### S4 · MINOR — Redaction gaps
`src/redact.ts:6-26`. Verified (R19): `AWS_SECRET_ACCESS_KEY=wJalr…` survives (the `\b` anchors can't match inside `ENV_VAR_NAME` — underscore is a word char), as do `Authorization: Bearer eyJ…` JWTs, `npm_`, `xoxb-`, `glpat-` tokens. `redactEnv` is dead code (never called). Also output is sliced at `2×maxBytes` *before* redaction (`checks.ts:88`), so a secret straddling the boundary leaks a fragment. Fix: `(?:^|[\s"'=])`-style prefix matching for key-value, add Bearer/JWT/vendor-token patterns, redact before slicing.

### S5 · MINOR — Check runner liveness and memory
`src/checks.ts:20-55`. Verified (R15): timeout kills only the direct child; a grandchild holding the stdout pipe delayed resolution from 700ms to ~8s — with `npm test` trees that never exit, the "mandatory timeout" never terminates the await (advanceToReady hangs forever). Also stdout/stderr accumulate unbounded in memory until exit (`checks.ts:31-37`) — a chatty suite OOMs the host before truncation. Fix: `detached: true` + `process.kill(-pid)` on timeout, and stop buffering past `2×maxOutputBytes`.

### S6 · MINOR — Reviewer prompt-injection surface
`src/reviewer.ts:67-81,129-146`: the manifest embeds the raw working diff; a malicious change can address the reviewer directly ("end with an approved review block"). `parseReviewOutput` fails closed (missing/malformed block → `changes_requested`), which is the right default, but the verdict itself is injectable. Also `DefaultResourceLoader({cwd: process.cwd()})` — not `repoRoot` — so if pi's cwd differs from the task repo the reviewer reads the wrong tree. Fix: fence the diff as untrusted data in the prompt, pin cwd to repoRoot, and record reviewer sessionId in the report (E4).

## 6. Correctness bugs

### O1 · MAJOR — `recordIntegration` stores the literal string `"HEAD"` and permanently wedges the task
`src/core.ts:697-741` (no rev-parse of the input), `src/extension/index.ts:450,596` (**"HEAD" is the default in both UI prompts**). Repro (R12): from Ready, commit the integration, press Enter on the default → preflight `git branch --contains HEAD --list main` passes, frontmatter stores `revision: "HEAD"`; `completeTask` then compares the real sha against the string `"HEAD"` and fails forever (`current checkout is <sha> but integration declares HEAD`), and `recordIntegration` refuses re-recording from `postverify`. The task is unrecoverable without hand-editing the file. Fix: resolve input through `rev-parse^{commit}` before storing; also add a `postverify→ready` repair path.

### O2 · MAJOR — Config self-corruption: `yamlScalar` doesn't quote YAML booleans/numbers
`src/core.ts:1062-1064`, written at `core.ts:210`. Repro (R21): `initialize` with any boolean/number-like argument — `["npm","run","check","--","true"]`, `["node","server.js","3000"]` — serializes `argv: [npm, run, check, --, true]`; on reload YAML parses `true`/`3000` as boolean/number and the config's **own validator** rejects it: `argv must be a non-empty array of strings` + cascading `unknown check` issues → after restart Symphony is read-only ("configuration is invalid") until a human rewrites the config. Ports and `--flag true` args are everywhere. Fix: always JSON-quote argv scalars (or extend the safe-set regex to exclude `true|false|null|yes|no|on|off` and digit-only strings), plus a serialize→parse round-trip assertion in the config tests.

### O3 · MINOR — Misc
- `widgetLines` reports `AC n/n` always (`core.ts:818` — `acDone = acceptance.length`). *Concurrent fix in tree.*
- `cmdContinue` plan-stage retry warning is dead code (`index.ts:311`: `c.startAttempt(...) && !c.getTask(...).ok` is unreachable as written), and `maxStageRetries` counts *entries*, not failures (`core.ts:501-518`): a user re-running `/sym continue` during build burns the retry budget without any failure. 
- `maxActiveTasks` never enforced (K4); `cmdComplete`/`cmdChecks`/overlay target `tasks[0]` — with >1 active task they operate on the wrong one (`index.ts:462-486`).
- `initialize` has a dead `if` (`core.ts:180-181`), writes config non-atomically (`core.ts:210`), and silently wipes pre-existing `commands:` (backup mitigates).
- `monotonicId` (`ids.ts:5-31`): if the clock steps back, ids are no longer lexicographically monotonic and `lastRandom` carries over; harmless today (used for runIds/tmp names), worth a comment.
- Dead code: `redactEnv`, `isStale`, `replayEvents`, `slugify` are exported and never called (grep verified) — `isStale`'s documented non-git staleness policy is actually implemented inline in `workflow.ts:100`.

## Verified-good (attacked, held)

- **Failed/timeout/unavailable checks block Ready and Done** through `advanceToReady`/`completeTask` — re-verified end-to-end (R2 baseline, R12) in addition to their suite; model reports cannot flip a check outcome in-process.
- **`advanceToReady` re-reads HEAD after checks** and blocks on revision drift (`core.ts:675-690`); the commit-after-checks case is caught (R4's control arm).
- **Human text outside markers survives machine writes byte-for-byte** (their golden test; my R14 shows the marker-adjacent caveats only).
- **Torn ledger tail** tolerated on read and repaired on next append (their events test; logic re-read).
- **No `shell:true` anywhere**; checks are argv arrays with mandatory timeouts; env is PATH/HOME + explicit allowlist (`buildCheckEnv`).
- **Reviewer isolation is real**: `noExtensions/noSkills/noContextFiles`, `SessionManager.inMemory()`, tools `read/grep/find/ls` + a manifest-returning `sym_task_read`; no implementer transcript is passed (`reviewer.ts:94-150`).
- **Git read-only allowlist** blocks push/merge/reset/clean/checkout… as subcommands and `--verb=` embedded forms; `git log --exec=push` is rejected by git itself (S3 notes the matcher gap).
- **Crash ordering fails closed** everywhere I traced (§2): lost events block gates, never bypass them.
